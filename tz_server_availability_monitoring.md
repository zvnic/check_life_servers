# Техническое задание

## Система мониторинга доступности и живучести объектовых серверов Check Life Servers (CLS)

**Версия:** 1.1  
**Дата:** 27.07.2026  
**Статус:** проект требований

---

## 1. Назначение системы

Разработать централизованную систему мониторинга серверов, размещённых на удалённых объектах и подключённых к Интернету через сети мобильных операторов.

Объектовый сервер самостоятельно, с заданной периодичностью, выполняет исходящие HTTPS-запросы к API системы мониторинга и передаёт:

- сигнал доступности (`heartbeat`);
- техническое состояние сервера;
- состояние мобильного подключения;
- прикладные метрики;
- расширяемый набор пользовательских метаданных.

Система мониторинга должна сохранять историю, определять периоды доступности и недоступности, выявлять инциденты, отображать текущее состояние на дашборде и формировать аналитические отчёты.

## 2. Особенности эксплуатации

- объектовый сервер может находиться за CGNAT без белого IP-адреса;
- входящие подключения к объектовому серверу не требуются;
- внешний IP мобильного оператора может динамически меняться;
- связь может иметь высокую задержку, потери пакетов и кратковременные разрывы;
- системное время объектового сервера может отличаться от времени монитора;
- после восстановления связи возможна передача накопленной телеметрии;
- перечень метаданных и контролируемых показателей должен расширяться без изменения основной схемы API.

## 3. Термины

| Термин | Значение |
|---|---|
| Агент | Лёгкий сервис на объектовом сервере, отправляющий данные в монитор |
| Монитор | Центральный backend, принимающий и анализирующий телеметрию |
| Heartbeat | Периодический запрос, подтверждающий доступность объекта |
| Объект | Контролируемый сервер или программно-аппаратный комплекс |
| Инцидент | Зафиксированный период недоступности или деградации |
| Живучесть | Способность сервера и агента продолжать работу и восстанавливаться после сбоев |
| SLA | Доля времени доступности за расчётный период |

## 4. Границы системы

### 4.1. В состав решения входят

- агент объектового сервера;
- публичный HTTPS API приёма heartbeat и телеметрии;
- сервис расчёта состояний и инцидентов;
- хранилище конфигурации, событий и временных рядов;
- web-дашборд;
- генератор аналитических отчётов;
- подсистема уведомлений;
- административный интерфейс;
- аудит действий и наблюдаемость самой системы мониторинга.

### 4.2. В первую версию не входят

- удалённое выполнение произвольных команд на объекте;
- удалённый shell;
- автоматическое управление оборудованием;
- обязательный входящий ICMP/TCP-контроль объекта;
- тарификация и биллинг.

## 5. Архитектура

### 5.1. Модель взаимодействия

Использовать модель **agent push / outbound-only**:

1. Агент собирает локальные показатели.
2. Агент отправляет heartbeat по HTTPS.
3. API аутентифицирует объект и фиксирует серверное время приёма.
4. Источник запроса используется для определения внешнего IP.
5. Сервис анализа обновляет текущее состояние и при необходимости открывает или закрывает инцидент.
6. Данные сохраняются для построения графиков и отчётов.

Отсутствие входящего доступа позволяет системе работать за NAT и CGNAT.

### 5.2. Рекомендуемые компоненты

| Компонент | Рекомендуемая реализация |
|---|---|
| Backend API | Python 3.12, FastAPI, Pydantic v2 |
| Основная БД | PostgreSQL 16 |
| Временные ряды | TimescaleDB либо секционированные таблицы PostgreSQL |
| Кеш и состояние | Redis |
| Фоновые задачи | Celery, Dramatiq или arq |
| Frontend | React/Vue 3, TypeScript |
| Графики | Apache ECharts |
| Агент | Python или Go, systemd-сервис |
| Развёртывание | Docker Compose; поддержка Kubernetes как опция |
| Наблюдаемость | Prometheus, Grafana, OpenTelemetry |

Система должна допускать замену отдельных компонентов без изменения публичного контракта агента.

## 6. Состояния объекта

Поддержать следующие состояния:

| Состояние | Условие |
|---|---|
| `unknown` | Heartbeat ещё не поступал либо объект только зарегистрирован |
| `online` | Последний heartbeat принят в допустимом интервале, критических нарушений нет |
| `degraded` | Heartbeat поступает, но нарушены заданные пороги метрик |
| `unstable` | За окно наблюдения превышено число кратковременных разрывов или сильно выросла задержка |
| `offline` | Heartbeat отсутствует дольше порога недоступности |
| `maintenance` | Активно согласованное окно технического обслуживания |
| `disabled` | Мониторинг объекта отключён администратором |

Пример параметров по умолчанию:

- интервал heartbeat — 60 секунд;
- допустимая задержка — 30 секунд;
- переход в `offline` — после трёх пропущенных heartbeat, но не ранее 180 секунд;
- переход в `online` после сбоя — после двух последовательных успешных heartbeat;
- параметры должны настраиваться глобально и отдельно для каждого объекта.

Использовать гистерезис, чтобы исключить частое переключение состояний при нестабильной мобильной связи.

## 7. Функции агента

Агент должен:

- запускаться автоматически вместе с ОС;
- работать как отдельный непривилегированный системный пользователь;
- периодически собирать и отправлять данные;
- иметь настраиваемые таймауты, интервалы и случайный `jitter`;
- повторять запросы с экспоненциальной задержкой;
- сохранять непереданную телеметрию в локальную ограниченную очередь;
- ограничивать размер и срок хранения локальной очереди;
- корректно продолжать работу после перезапуска;
- передавать уникальный `event_id`, монотонный `sequence` и локальное время измерения;
- поддерживать удалённое получение безопасной конфигурации мониторинга;
- не выполнять произвольный код, полученный от центрального сервера;
- вести локальный журнал с ротацией;
- предоставлять локальную команду самодиагностики;
- поддерживать автоматическое обновление только подписанными пакетами, если эта функция будет включена.

### 7.1. Базовые метрики агента

- hostname;
- версия ОС и ядра;
- версия агента;
- uptime ОС и агента;
- загрузка CPU;
- load average;
- общий и свободный объём RAM;
- swap;
- использование файловых систем;
- температура, если датчики доступны;
- состояние контролируемых процессов и контейнеров;
- количество перезапусков агента;
- состояние локальной очереди;
- локальный IP и активный сетевой интерфейс;
- тип подключения;
- объём переданных и принятых данных;
- при наличии модема: оператор, тип сети, уровень сигнала, ICCID/IMEI в маскированном виде;
- прикладной результат внутренних health-check серверных сервисов.

Сбор чувствительных идентификаторов оборудования должен отключаться настройкой.

## 8. Приём heartbeat и телеметрии

### 8.1. Основной endpoint

`POST /api/v1/agents/heartbeat`

Пример запроса:

```json
{
  "schema_version": "1.0",
  "event_id": "018fb8d7-3b12-7b53-b921-67fd1df9bb51",
  "server_id": "srv_object_001",
  "sequence": 18442,
  "measured_at": "2026-07-26T18:41:20.531Z",
  "agent": {
    "version": "1.0.0",
    "uptime_seconds": 98322
  },
  "system": {
    "hostname": "edge-01",
    "os": "Ubuntu 24.04",
    "kernel": "6.8.0",
    "uptime_seconds": 351840,
    "cpu_usage_percent": 24.7,
    "memory_usage_percent": 61.2,
    "disk_usage_percent": 72.1
  },
  "network": {
    "interface": "wwan0",
    "local_ip": "10.41.18.7",
    "operator": "operator_name",
    "network_type": "LTE",
    "signal": {
      "rssi_dbm": -79,
      "rsrp_dbm": -103,
      "rsrq_db": -12,
      "sinr_db": 10
    }
  },
  "services": [
    {
      "name": "application",
      "status": "up",
      "latency_ms": 18
    }
  ],
  "metadata": {
    "object_name": "Объект №1",
    "region": "Липецкая область",
    "hardware_model": "HP EliteDesk"
  }
}
```

Пример ответа:

```json
{
  "accepted": true,
  "event_id": "018fb8d7-3b12-7b53-b921-67fd1df9bb51",
  "received_at": "2026-07-26T18:41:21.104Z",
  "server_time": "2026-07-26T18:41:21.107Z",
  "next_heartbeat_seconds": 60,
  "configuration_version": 7
}
```

### 8.2. Правила обработки

- Истинным временем получения heartbeat считать время центрального сервера `received_at`.
- `measured_at` использовать для телеметрии, но не как единственный источник расчёта доступности.
- Внешний IP определять по сетевому источнику запроса после обработки списка доверенных reverse proxy.
- Заголовки `X-Forwarded-For` принимать только от явно заданных доверенных proxy.
- Переданный агентом внешний IP считать справочным и не использовать как доказанный.
- Обеспечить идемпотентность по `server_id + event_id`.
- Повторный пакет не должен создавать повторные события и инциденты.
- Историческая телеметрия из локальной очереди должна сохраняться с признаком `is_delayed`.
- Доставленные после восстановления исторические пакеты не должны задним числом изменять факт отсутствия связи с монитором.
- Фиксировать расхождение времени агента и монитора.
- Отклонять слишком большой пакет и неизвестные обязательные версии схемы с понятным кодом ошибки.
- Неизвестные поля внутри расширяемых секций не должны нарушать приём сообщения.

### 8.3. Дополнительные endpoints

- `POST /api/v1/agents/telemetry/batch` — пакетная доставка накопленных измерений;
- `GET /api/v1/agents/config` — получение конфигурации агента;
- `POST /api/v1/agents/events` — отправка перезапусков, ошибок и иных событий;
- `GET /api/v1/health/live` — работоспособность API;
- `GET /api/v1/health/ready` — готовность API и зависимостей;
- административные endpoints для объектов, пользователей, отчётов и окон обслуживания.

## 9. Расширяемые метаданные

Метаданные должны поддерживаться в двух формах:

1. системные типизированные поля для фильтрации и аналитики;
2. расширяемый объект `metadata` формата JSON.

Администратор должен иметь возможность создать описание пользовательского поля:

- ключ;
- отображаемое название;
- тип: строка, число, логическое значение, дата, справочник;
- единица измерения;
- обязательность;
- допустимый диапазон;
- доступность в фильтрах;
- доступность в отчётах;
- признак чувствительности;
- срок хранения.

Для часто используемых полей предусмотреть индексирование JSONB или вынесение в типизированную таблицу без изменения контракта агента.

## 10. Расчёт доступности

### 10.1. Основные показатели

Для объекта и группы объектов рассчитывать:

- доступность за сутки, неделю, месяц, квартал и произвольный период;
- общую длительность доступности;
- общую длительность недоступности;
- число инцидентов;
- MTBF — среднее время между отказами;
- MTTR — среднее время восстановления;
- максимальную и среднюю длительность инцидента;
- долю нестабильной работы;
- число смен внешнего IP;
- время работы на каждом внешнем IP и операторе;
- статистику задержки heartbeat;
- p50, p95 и p99 задержки;
- процент потерянных/просроченных heartbeat;
- время деградации по CPU, памяти, диску, температуре, сигналу и сервисам.

### 10.2. Формула

```text
Доступность, % =
  (расчётное время − незапланированный простой)
  / расчётное время × 100
```

Из расчётного времени могут исключаться согласованные окна обслуживания. В отчёте одновременно показывать:

- фактическую доступность с учётом всех простоев;
- SLA-доступность без согласованных окон обслуживания.

### 10.3. Границы инцидента

- начало инцидента: время первого ожидаемого, но не полученного heartbeat с учётом grace period;
- подтверждение: достижение порога `offline`;
- окончание: время первого heartbeat устойчивой серии восстановления;
- при расчёте допускается восстановить предполагаемую границу инцидента, но в данных должны храниться как расчётная, так и фактически подтверждённая границы;
- изменение настроек порогов не должно молча пересчитывать ранее закрытые отчётные периоды; пересчёт выполняется отдельной версионируемой операцией.

## 11. Контроль внешнего IP и мобильной сети

Для каждого heartbeat сохранять:

- внешний IPv4/IPv6, наблюдаемый монитором;
- порт источника — только при необходимости диагностики, с ограниченным сроком хранения;
- ASN;
- наименование сети/провайдера;
- страну и регион по GeoIP с указанием, что данные приблизительные;
- семейство IP;
- дату первого и последнего наблюдения IP;
- признак смены IP;
- мобильные показатели, переданные агентом.

При смене внешнего IP создавать информационное событие. Частоту смены IP отображать на графике. Геолокацию IP не считать точным местоположением объекта.

Обогащение ASN/GeoIP должно выполняться асинхронно и не блокировать приём heartbeat.

## 12. Дашборд

### 12.1. Главный экран

Отображать:

- общее число объектов;
- количество `online`, `degraded`, `unstable`, `offline`, `maintenance`;
- общую доступность за выбранный период;
- активные инциденты;
- объекты с наиболее низкой доступностью;
- объекты без данных;
- последние смены внешнего IP;
- карту объектов только по заданным администратором координатам, а не по GeoIP мобильного адреса.

### 12.2. Таблица объектов

Поля:

- название и идентификатор;
- группа, регион и объект;
- текущее состояние;
- время последнего heartbeat;
- длительность текущего состояния;
- доступность за 24 часа и 30 дней;
- внешний IP;
- оператор/ASN;
- тип мобильной сети;
- уровень сигнала;
- CPU, RAM, диск;
- версия агента;
- активный инцидент.

Поддержать поиск, сортировку, фильтры, сохранённые представления и экспорт.

### 12.3. Карточка объекта

Отображать:

- текущее состояние и длительность;
- временную шкалу состояний;
- график heartbeat и разрывов;
- график доступности;
- историю инцидентов;
- историю внешних IP;
- показатели мобильного сигнала;
- CPU, RAM, диск, температуру и uptime;
- состояния процессов/контейнеров/сервисов;
- системные и пользовательские метаданные;
- журнал событий;
- окна обслуживания;
- настройки порогов.

Графики должны поддерживать масштабирование, выбор периода, агрегацию, подсказки и синхронизацию курсора по времени.

## 13. Инциденты и уведомления

Система должна:

- автоматически открывать и закрывать инциденты;
- объединять последовательные краткие разрывы по настраиваемому правилу;
- поддерживать подтверждение инцидента оператором;
- позволять добавить комментарий, причину и принятые меры;
- фиксировать пользователя и время изменения;
- поддерживать категории причин;
- предотвращать шторм уведомлений;
- поддерживать эскалацию и повторные уведомления;
- отправлять уведомления о `offline`, восстановлении, деградации, нестабильности и смене IP.

Каналы первой очереди:

- email;
- webhook;
- Telegram.

Архитектура должна позволять добавить Max, Slack, Teams, SMS и другие каналы.

## 14. Аналитические отчёты

### 14.1. Виды отчётов

- отчёт по одному объекту;
- сводный отчёт по группе, региону или всем объектам;
- отчёт об инцидентах;
- отчёт по качеству мобильной связи;
- отчёт по сменам IP и операторов;
- отчёт по состоянию ресурсов;
- SLA-отчёт;
- сравнительный отчёт за два периода.

### 14.2. Содержание отчёта

- период и часовой пояс;
- список включённых объектов;
- методика и версия расчёта;
- фактическая и SLA-доступность;
- распределение времени по состояниям;
- количество и длительность инцидентов;
- MTBF и MTTR;
- лучшие и худшие объекты;
- динамика относительно предыдущего периода;
- графики;
- таблица инцидентов;
- окна обслуживания и исключённое время;
- изменения IP и сети;
- аномалии и выводы;
- отметка о неполных или запоздалых данных.

### 14.3. Форматы и расписание

- просмотр в web-интерфейсе;
- экспорт PDF, XLSX и CSV;
- автоматическое формирование по расписанию;
- доставка по email и webhook;
- неизменяемый снимок исходных параметров отчёта;
- хранение версии алгоритма расчёта.

- `notification_deliveries`;
- `report_definitions`;
- `generated_reports`;
- `audit_log`.

Сырые события heartbeat должны быть отделены от вычисленных интервалов состояния. Это необходимо для повторного анализа и аудита.

## 16. Безопасность

- только HTTPS, TLS 1.2+;
- предпочтительно индивидуальный mTLS-сертификат объекта;
- допустимый альтернативный вариант — короткоживущий JWT или уникальный API-ключ, хранимый в хешированном виде;
- независимая ротация и отзыв учётных данных каждого агента;
- RBAC для пользователей;
- опциональная мультитенантная изоляция;
- защита от replay-атак с использованием `event_id`, `sequence`, временного окна и подписи;
- rate limiting по объекту, tenant и IP;
- ограничение размера JSON и batch;
- валидация всех полей;
- маскирование токенов, IMEI, ICCID и персональных данных в логах;
- шифрование секретов;
- журналирование входов, изменений конфигурации, инцидентов и отчётов;
- резервное копирование и проверка восстановления;
- политика хранения и удаления телеметрии;
- запрет доверия произвольным proxy-заголовкам.

## 17. Надёжность самой системы мониторинга

Монитор не должен становиться единственной неконтролируемой точкой отказа.

Требования:

- API должно быть stateless и масштабироваться горизонтально;
- приём heartbeat должен оставаться быстрым при недоступности подсистемы отчётов;
- запись критического события подтверждается только после надёжного сохранения;
- фоновые обогащения и уведомления выполняются через очередь;
- внутренние health-check;
- метрики доступности самого монитора;
- резервное копирование БД;
- документированная процедура disaster recovery;
- целевые показатели: RPO не более 15 минут, RTO не более 60 минут;
- все компоненты должны автоматически перезапускаться;
- обновление без потери принятых heartbeat.

## 18. Производительность и хранение

Для первой версии принять расчётную нагрузку:

- до 1 000 объектов;
- heartbeat один раз в 60 секунд;
- не менее 50 запросов в секунду с запасом;
- API p95 не более 300 мс без учёта внешнего обогащения;
- обновление текущего статуса на дашборде не позднее 10 секунд после обработки;

Политика хранения по умолчанию:

- агрегаты 1 минута — 1 год;
- часовые и суточные агрегаты — 3 года;

## 27. Авторизация администратора

### 27.1. Первичная инициализация

В системе не должно быть встроенного логина или пароля по умолчанию. Первый пользователь с ролью `admin` создаётся после запуска миграций одной из команд:

```bash
make admin-create
make admin-create ADMIN_LOGIN=admin
```

Основной безопасный сценарий — интерактивный ввод пароля без отображения в терминале и повторное подтверждение. Команда должна выполняться внутри контейнера backend, проверять политику сложности, создавать пользователя транзакционно и завершаться ошибкой, если такой логин уже существует.

Для неинтерактивного CI/bootstrap допускается передача пароля только через временный Docker secret либо переменную `ADMIN_BOOTSTRAP_PASSWORD_FILE`, указывающую на смонтированный файл. Передача пароля аргументом командной строки (`ADMIN_PASSWORD=... make ...`) запрещается, поскольку значение может попасть в history и список процессов.

Допускается автоматическая генерация случайного пароля командой:

```bash
make admin-create-generated ADMIN_LOGIN=admin
```

Сгенерированный пароль показывается в терминале ровно один раз, не журналируется и не сохраняется приложением в открытом виде. После первого входа система должна потребовать его смену.

### 27.2. Хранение и защита пароля

- пароль не шифруется обратимо, а хешируется `Argon2id` с уникальной солью;
- параметры `Argon2id` хранятся вместе с хешем и выбираются по актуальной рекомендации OWASP с возможностью последующего rehash;
- в БД хранить `password_hash`, дату изменения, признак обязательной смены и счётчик неуспешных попыток;
- `.env` не должен содержать постоянный пароль администратора;
- если bootstrap-пароль временно поступил через `.env`, файл должен быть исключён из Git, иметь права `0600`, а значение должно быть удалено сразу после успешной инициализации;
- сессия web-интерфейса — защищённая cookie `HttpOnly`, `Secure`, `SameSite=Lax/Strict`; access-токены не хранить в `localStorage`;
- предусмотреть ограничение попыток входа, задержку/блокировку, завершение всех сессий, смену пароля и аудит входов;
- `CSRF`-защита обязательна для cookie-based сессий;
- сброс пароля выполняется одноразовым короткоживущим токеном либо локальной административной командой `make admin-reset-password`;
- секрет подписи сессий и иные ключи хранить в Docker secrets; `.env` использовать только для несекретной конфигурации в production;
- MFA/TOTP рекомендуется включить на втором этапе, а для Internet-facing production считать обязательным.

Минимальные роли MVP: `admin`, `operator`, `viewer`, `auditor`. Только `admin` управляет пользователями, enrollment-токенами, системными настройками и retention policy.

## 28. Регистрация и идентификация устройств

Добавление объекта выполняется не ручным копированием постоянного API-ключа, а через одноразовый enrollment:

1. Администратор создаёт в UI или API заявку на устройство, указывает название, группу, платформу и срок действия.
2. Backend генерирует криптографически случайный одноразовый enrollment token, хранит только его хеш и показывает токен один раз.
3. Генератор формирует платформенный установщик, содержащий URL монитора, идентификатор заявки и enrollment token.
4. Устройство вызывает `POST /api/v1/agents/enroll`, передаёт token, стабильный `installation_id`, публичный ключ устройства и первичные метаданные.
5. Сервер атомарно погашает token, создаёт объект и выдаёт уникальные долгоживущие credentials агента.
6. Агент сохраняет credentials с минимальными правами и далее использует их для heartbeat.
7. Повторное использование enrollment token отклоняется и фиксируется в аудите.

Рекомендуемый рабочий вариант для MVP — ключевая пара Ed25519 на устройстве и подпись каждого запроса. Сервер хранит публичный ключ, проверяет подпись над методом, URI, хешем тела, `event_id`, `sequence` и временем. Если на целевой платформе это невозможно, допускается индивидуальный API token, который хранится на сервере только в хешированном виде и передаётся исключительно по TLS.

Endpoint регистрации:

```text
POST /api/v1/agents/enroll
```

Успешный ответ должен включать `server_id`, версию конфигурации, интервал heartbeat и credential/certificate только в момент выдачи. Enrollment token имеет TTL не более 30 минут по умолчанию, действует один раз и может быть отозван до использования.

Необходимо различать:

- `server_id` — серверный неизменяемый идентификатор объекта;
- `installation_id` — идентификатор конкретной установки агента;
- `credential_id` — идентификатор ключа, допускающий ротацию;
- `boot_id` — идентификатор загрузки ОС для анализа перезапусков;
- `sequence` — монотонный счётчик в пределах credential/installation.

Клонирование файловой системы с уже зарегистрированным агентом должно обнаруживаться. Одновременные heartbeat с одним credential и разными fingerprint/boot context создают событие безопасности.

## 29. Генерация и установка агентов

### 29.1. Общие требования к генератору

В административном интерфейсе и CLI должна быть команда «Создать установщик». На входе:

- платформа и версия;
- архитектура (`amd64`, `arm64`, `mips`, `mipsel` и другие поддерживаемые);
- URL публичного API;
- объект/группа и разрешённые метаданные;
- интервал heartbeat и перечень health-check;
- срок действия enrollment token;
- SHA-256 fingerprint доверенного CA при использовании частного PKI.

На выходе формируется короткоживущий установочный bundle либо команда скачивания. Bundle должен иметь срок действия, checksum и цифровую подпись. Токен нельзя помещать в публичный постоянный URL или журнал web-сервера; предпочтительна выдача временного файла после авторизации администратора.

Команды центрального сервиса:

```bash
make agent-bundle PLATFORM=ubuntu ARCH=amd64 SERVER_NAME=edge-01
make agent-bundle PLATFORM=openwrt ARCH=mipsel SERVER_NAME=router-01
make agent-bundle PLATFORM=routeros ARCH=arm64 SERVER_NAME=mikrotik-01
make agent-token-revoke TOKEN_ID=<id>
```

В сгенерированном установщике должны быть команды проверки checksum/signature, регистрации, проверки первого heartbeat и удаления enrollment token с устройства.

### 29.2. Ubuntu Server

Предпочтительный агент — статический Go-бинарный файл без runtime-зависимостей. Bundle содержит:

- подписанный бинарный файл под выбранную архитектуру;
- `install.sh`;
- unit-файл `systemd`;
- шаблон конфигурации;
- checksum и подпись;
- одноразовый enrollment-файл с правами `0600`.

Установщик создаёт отдельного системного пользователя без shell, каталоги `/etc/cls-agent` и `/var/lib/cls-agent`, выполняет enrollment, удаляет одноразовый token, включает hardening unit-файла и запускает сервис. Локальная очередь хранится в `/var/lib/cls-agent` с ограничением размера.

### 29.3. OpenWrt

Для OpenWrt формируется пакет `.ipk` под поддерживаемую архитектуру либо минимальный bundle с `procd` init script. Агент не должен требовать Docker на роутере. Предпочтительны статический бинарный файл или `ucode`; shell-вариант допустим только как ограниченный MVP.

Интеграция должна использовать:

- UCI-конфигурацию `/etc/config/cls-agent`;
- `procd` для автозапуска и рестарта;
- `ubus`/`jsonfilter` для метаданных и состояния интерфейсов;
- системный CA bundle и проверку TLS;
- ограниченную очередь с учётом flash wear;
- `logread` без вывода credentials.

### 29.4. MikroTik RouterOS

Название платформы в документации — **MikroTik RouterOS**. RouterOS не следует считать обычной Linux-системой и нельзя требовать от него Docker/systemd. Для RouterOS 7 генератор создаёт `.rsc`-скрипт импорта, который:

- создаёт минимально привилегированного пользователя/группу и environment-параметры;
- регистрирует устройство через `/tool fetch` по HTTPS;
- создаёт `/system scheduler` для периодического запуска heartbeat;
- собирает только доступные RouterOS метрики;
- использует проверку сертификата (`check-certificate=yes`);
- не пишет token/credential в log;
- поддерживает jitter, ограниченные повторы и безопасную ротацию credential.

Из-за ограничений RouterOS расширенная локальная очередь, Ed25519-подпись и некоторые системные метрики могут быть недоступны. Эти различия должны явно отражаться в capability-профиле агента. Для повышенных требований безопасности рекомендуется внешний агент на OpenWrt/Linux-шлюзе либо mTLS, если конкретная версия RouterOS поддерживает необходимый сценарий.

### 29.5. Capability negotiation

При enrollment агент передаёт `capabilities`, например:

```json
{
  "platform": "routeros",
  "platform_version": "7.20",
  "architecture": "arm64",
  "capabilities": [
    "heartbeat",
    "resource_metrics",
    "interface_metrics",
    "scheduler",
    "tls_verify"
  ]
}
```

Backend не должен считать отсутствие неподдерживаемой метрики деградацией. Пороговые правила применяются только к объявленным и разрешённым capabilities.

## 30. Docker-only и Makefile

Требование «только Docker» относится ко всей центральной части, инструментам разработки, тестам, миграциям и генератору bundle. Платформенные агенты являются исключением: Ubuntu запускает нативный systemd-сервис, OpenWrt — `procd`, RouterOS — scheduler script, поскольку Docker там отсутствует или эксплуатационно нецелесообразен.

В корне репозитория должен находиться `Makefile` как единая документированная точка входа. Он не должен скрыто использовать локальные Python/Node runtime. Обязательные цели:

```text
make help                    показать команды и необходимые параметры
make env                     создать .env из .env.example без секретов
make secrets                 создать локальные Docker secrets с правами 0600
make build                   собрать все образы
make up                      запустить production-like стек
make down                    штатно остановить стек без удаления данных
make restart                 пересоздать контейнеры
make ps                      показать состояние и health
make logs [SERVICE=api]      показать журналы
make migrate                 выполнить миграции из нового backend-образа
make admin-create            интерактивно создать первого администратора
make admin-create-generated  создать временный случайный пароль
make admin-reset-password    безопасно сменить пароль
make test                    выполнить все тесты в контейнерах
make test-unit               unit-тесты
make test-integration        интеграционные тесты
make lint                    lint/format/typecheck в контейнерах
make load-test               нагрузочный профиль
make agent-bundle            создать платформенный bundle
make backup                  создать проверяемую резервную копию
make restore BACKUP=<path>   восстановить явно указанный backup
make doctor                  проверить Docker, Compose, env, secrets и health
make clean                   удалить только сборочные артефакты
```

Цели удаления volumes или production-данных не включать в обычный `clean`. Для потенциально разрушительных операций использовать отдельную явно названную команду с интерактивным подтверждением и проверкой Compose project name.

Рекомендуемая структура:

```text
.
├── Makefile
├── compose.yaml
├── compose.dev.yaml
├── .env.example
├── docker/
├── backend/
├── frontend/
├── agent/
│   ├── core/
│   └── platforms/
│       ├── ubuntu/
│       ├── openwrt/
│       └── routeros/
├── scripts/
│   ├── admin-create.sh
│   ├── agent-bundle.sh
│   ├── backup.sh
│   ├── restore.sh
│   └── doctor.sh
└── tests/
```

Скрипты должны использовать строгий режим shell, валидировать обязательные параметры, не печатать секреты, иметь предсказуемые exit codes и запускаться через Make. В production Compose необходимо:

- закреплять версии образов, не использовать `latest`;
- запускать контейнеры от непривилегированных пользователей и с read-only filesystem, где возможно;
- удалять лишние Linux capabilities и включать `no-new-privileges`;
- публиковать только `80/443` reverse proxy, а административный UI защищать авторизацией;
- использовать внутренние сети для PostgreSQL, Redis и workers;
- задавать healthcheck, restart policy, resource limits и ротацию логов;
- выполнять миграции одноразовым контейнером из того же нового образа, который развёртывается;
- не встраивать секреты в image layers и frontend bundle.

## 31. Графики и аналитика Uptime

Чтобы аналитика оставалась воспроизводимой, хранить три слоя данных:

1. неизменяемые сырые heartbeat/telemetry;
2. вычисленные интервалы состояний с версией алгоритма;
3. агрегаты по минутам, часам и дням.

Граница bucket и отчётного периода вычисляется в UTC, а отображение выполняется в выбранной IANA timezone. Для каждого графика UI должен показывать качество данных: задержанные пакеты, пропуски, clock skew, maintenance и период, за который сырые данные уже удалены.

Минимальный набор визуализаций:

- календарь доступности по дням;
- state timeline (`online`, `degraded`, `unstable`, `offline`, `maintenance`, `unknown`);
- uptime/SLA процент по дням, неделям и месяцам;
- scatter/line heartbeat latency с p50/p95/p99;
- ожидаемые, принятые, просроченные и потерянные heartbeat;
- длительность и частота инцидентов, MTBF и MTTR;
- CPU/RAM/disk/temperature совместно с интервалами деградации;
- качество мобильного сигнала и тип сети;
- смены внешнего IP, ASN и оператора;
- версия агента и перезапуски на временной шкале;
- рейтинг объектов и сравнение выбранных периодов.

Для текущего статуса используется только серверное время приёма. Исторический пакет улучшает графики телеметрии, но не переписывает задним числом подтверждённый монитором uptime. Любой административный пересчёт создаёт новую версию результата и оставляет предыдущую доступной для аудита.

API временных рядов должен выбирать подходящую агрегацию по диапазону и разрешению экрана, ограничивать число точек и возвращать признак неполных данных. Предварительные continuous aggregates/материализованные представления должны обновляться асинхронно и не замедлять heartbeat ingestion.

## 32. Рекомендации по реализации

### 32.1. Предлагаемый MVP-стек

- FastAPI + Pydantic v2 для API;
- PostgreSQL 16 + TimescaleDB для событий, интервалов и агрегатов;
- Redis + arq/Dramatiq для фоновых задач; Celery использовать только если необходимы его более сложные возможности;
- React + TypeScript + Apache ECharts для UI;
- Go для общего агента Ubuntu/OpenWrt;
- отдельный ограниченный RouterOS script adapter;
- Caddy, Traefik или Nginx как единственная публичная точка TLS;
- Prometheus/OpenTelemetry для наблюдаемости, Grafana — для технических внутренних метрик монитора.

Не рекомендуется строить пользовательский продуктовый dashboard непосредственно в Grafana: собственный UI лучше обеспечивает RBAC, аудит, карточки объектов, workflow инцидентов и единый API.

### 32.2. Разделение backend

На старте достаточно модульного монолита с отдельными процессами:

- `api` — быстрый приём и чтение;
- `state-worker` — переходы состояний и инциденты;
- `aggregation-worker` — uptime и downsampling;
- `notification-worker` — уведомления;
- `report-worker` — тяжёлые экспорты.

Это снижает операционную сложность по сравнению с преждевременными микросервисами, но оставляет возможность горизонтального масштабирования. Приём heartbeat должен выполнять только валидацию, аутентификацию и надёжную запись; GeoIP, отчёты и уведомления остаются асинхронными.

### 32.3. Приоритет разработки

Рекомендуемый порядок:

1. Зафиксировать OpenAPI enrollment/heartbeat и модель времени.
2. Реализовать неизменяемое хранение событий и идемпотентность.
3. Реализовать state machine и контрольные наборы uptime/SLA.
4. Создать Ubuntu-агент и симулятор тысяч устройств.
5. Реализовать admin bootstrap, RBAC и аудит.
6. Создать dashboard, incident workflow и базовые агрегаты.
7. Добавить generator bundles, затем OpenWrt и RouterOS adapters.
8. Добавить уведомления, отчёты, backup/restore и нагрузочные проверки.

До разработки UI необходимо подготовить набор «золотых» временных сценариев: нормальная работа, единичный пропуск, длительный offline, flapping, maintenance, delayed batch, clock skew и смена правил. Ожидаемые интервалы и проценты uptime для них должны стать автоматическими тестами и эталоном аналитики.
